# Правила совместной работы: Claude ⇄ Codex (PLANNER)

> **Это файл ПРАВИЛ** (стабильный, редко меняется).
> Доска / план задач / состояние / locks / Q&A / арх-решения → **`docs/COLLAB_BOARD.md`**.
> Накопленный опыт (грабли, чтобы не повторять ошибки) → **`docs/COLLAB_LESSONS.md`**.
>
> Протокол перенесён из проверенного опыта `sprint-planner-cloud` и адаптирован под
> vanilla-стек и слои PLANNER. Память Claude НЕ видна Codex (и наоборот) — вся
> координация только через эти файлы + сообщения коммитов.
> **В начале КАЖДОЙ задачи (новой ИЛИ исправления) оба агента читают все три файла:**
> правила (этот), `COLLAB_BOARD.md` (что в работе) и `COLLAB_LESSONS.md` (грабли).

## 0. Роли

- **Оркестратор — пользователь.** Только он назначает задачи, расставляет
  приоритеты, назначает владельца релиза/merge. Может в ЛЮБОЙ момент остановить
  любого агента («стоп Claude» / «стоп Codex») и поставить задачу любому из них.
- **Назначенный агент отвечает за свою задачу end-to-end:** план → исполнение →
  гейт качества → отчёт с метриками. Контролирует, что задача реально выполнена
  (не «хендлер вызван», а «фича работает» — реальный прогон/браузер).
- **Claude** — домен/логика/данные, типы/контракты, сервисы, стор, утилиты,
  доменные и architecture-тесты, persistence, инфра/CI/конфиги, доки, ревью.
- **Codex** — UI (`js/ui`, `css`, `icons`), UI/visual/a11y/mobile-тесты, e2e.

## 1. Зоны (по умолчанию правим ТОЛЬКО свою)

| Зона | Владелец | Пути |
|---|---|---|
| UI / визуал | **Codex** | `js/ui/**`, `css/**`, `icons/**` |
| Домен / логика / данные | **Claude** | `js/domain/**`, `js/services/**`, `js/state/**`, `js/utils/**`, `js/types/**` |
| Контроллеры (оркестрация) | **координируется (lock)** | `js/controllers/**`, `js/app/**` — трогают и DOM, и Store |
| Тесты | по зоне | unit — у владельца кода; visual/a11y/mobile e2e — Codex; доменные/architecture — Claude |
| Инфра / релиз / харнесс | **Claude** | `scripts/**`, `.github/**`, `jest.config.cjs`, `playwright.config.js`, `eslint.config.js`, `babel.config.cjs` |
| Документация | по зоне автора | `docs/**` (общие `ARCHITECTURE.md`/`UserManual.md` — под lock) |
| **Общие (нужен lock)** | — | `index.html`, `manifest.json`, `sw.js`, `package.json`, `package-lock.json`, `js/config/commands.js`, `js/vendor/**`, `docs/COLLAB*.md`, `docs/ARCHITECTURE.md`, `docs/UserManual.md` |

**Нужно править чужую зону?** Не правь — поставь задачу владельцу в «Очередь» доски
(`COLLAB_BOARD.md`). Исключение — тривиальная правка по явному разрешению
пользователя («правь сам»); тогда фиксируй файл в lock на доске.

## 2. Главное правило против помех — «свою зону правлю, общие — под lock»

1. **Zone-first.** Вне своей зоны не редактируем.
2. **Lock общих файлов.** Перед правкой общего файла — впиши его в «Файлы-lock» на
   доске со своим именем. Залочен другим — не трогай, согласуй через «Очередь» или
   жди снятия. Снимай lock сразу после коммита/паузы.
3. **Коммить СВОЁ маленькими порциями.** Каждый агент коммитит свою завершённую
   работу сам (`git add` поимённо, gate зелёный). **Коммит ≠ merge/релиз.**
4. **Не отдавай управление с красным деревом.** Перед паузой/передачей — `npm test`
   (для UI/релиза — затронутый e2e) зелёный. Остановился на красном — пометь в
   «Состоянии» доски `RED` + упавший шаг.
5. **Правки общих файлов — по уникальному ТЕКСТ-якорю, не по номерам строк; при
   коллизии re-read + retry; уважай lock.**

## 3. Shared-tree verify-contamination (КРИТИЧНО для рефакторинга)

Оба агента на ОДНОМ working tree → локальный `npm test` видит uncommitted-правки
ОБОИХ → может пройти зелёным на ещё-не-запушенном коде партнёра; чистый CI краснеет.
Рефакторинг = масса контракт-изменений (move/rename/export/тип/новый ESM-модуль) →
класс особенно опасен. **Правило:** контракт-изменение (экспорт / имя helper'а /
сигнатура / перемещение модуля / новый файл в `sw.js`-precache) автор коммитит+пушит
**ПЕРВЫМ**, зависимый код — после pull. Авторитетен CI-exit последнего прогона, не
локальный verify. См. `COLLAB_LESSONS.md`.

## 4. Merge/релиз — ОДИН владелец + freeze + named GO

- Текущие `RELEASE OWNER` и `FREEZE` — в «Состоянии» доски. `none` → никто не
  мёрджит/тегает.
- Любое действие с shared state (merge рефактора в `main`, tag, публикация) — только
  текущим RELEASE OWNER и только по **поимённому GO** пользователя. OWNER ставит
  `FREEZE: on`, второй агент завершает атомарную правку и встаёт на паузу.
- **Авто-назначение:** когда очередь пуста (всё `accepted`), merge/tag выпускает тот
  агент, кто ПОСЛЕДНИМ выполнял работу из очереди; он берёт `RELEASE OWNER` на доске.
- ⚠ **Downstream `sprint-planner` / `FOR_USERS` / GitHub Release — OUT OF SCOPE
  текущего рефакторинга.** Даже RELEASE OWNER их НЕ трогает. Release-chain по
  умолчанию из `CLAUDE.md` для этой работы ОТКЛЮЧЁН.
- После успешного merge OWNER **чистит `COLLAB_BOARD.md`** — переносит `done`/
  `accepted`/`stale` записи в архив, оставляя только живое.

## 5. Контроль качества ДО коммита

1. **Self-gate (обязательно):** автор перед своим коммитом прогоняет ВСЕ применимые
   линии защиты, не только Jest: `npm run lint`, `npm test`, coverage gate,
   затронутый `npm run test:e2e`, `npm audit`, `npm run docs:manual-check`, CSS
   budget, architecture guards. Цифры из реального прогона, per-line с `[EXIT=N]`.
2. **Кросс-review ОБЯЗАТЕЛЕН (acceptance-gate, §6).** Завершённую работу одного
   агента независимо проверяет ВТОРОЙ — read-only ревью diff'а, каждый пункт с
   `file:line`, статус ✅verified / ⚠️false-positive / 🟡feature / ❓inconclusive.
   Особо строго: persistence/миграции, security, межмодульные контракты.
3. **Проверка КЛАССИФИКАЦИИ.** Каждая правка помечена одним тегом: `behavior-preserving`
   / `intentional behavior change` / `bug fix` / `security fix` / `UX copy-only` /
   `test-only` / `docs-only` / `deferred`. Ревьюер проверяет тег: `behavior-preserving`
   обязан иметь characterization-тест, доказывающий идентичность; behavior-изменение
   под видом `behavior-preserving` → REWORK. `intentional behavior change` — только
   после одобрения пользователя.
4. **Справка как часть Definition of Done.** При изменении видимого пользователю
   поведения автор синхронно правит `docs/UserManual.md` (и сверяется с реальным UI,
   не «по памяти»). Чисто внутренний рефакторинг — явно отметить «поведение не
   изменилось, Справка не требует правок».

## 6. Acceptance-gate, доработка и анти-петля

- **Статус-флоу задачи (на доске):** `in_progress → done → accepted-by-<partner>`.
  Задача НЕ закрыта, пока партнёр не поставил `accepted`. Агент НЕ берёт следующую
  СВОЮ задачу до акцепта предыдущей.
- **Анти-deadlock:** пока ждёшь акцепт — обязан вести верификацию/акцептацию работ
  ПАРТНЁРА (read-only review — это НЕ «своя следующая задача»). Простаивать запрещено.
- **Вердикт за один проход:** ✅ACCEPT либо ❌REWORK со списком дефектов
  (`file:line` + severity). **Молчаливый блок запрещён:** нет названного дефекта = принято.
- **Анти-петля: ≤2 круга rework**, дальше — accept с follow-up-заметкой.
- **Tie-break при разногласии:** (1) соответствие документированной архитектуре
  (`docs/ARCHITECTURE.md`) → (2) gate зелёный → (3) меньший blast-radius → (4) проще
  → (5) меньше нового кода. В своей зоне финальное слово — у владельца зоны.
- **Эскалация к пользователю — только если ОБА согласны, что заблокированы**, и с
  готовым рекомендованным вариантом, не открытым вопросом.

## 7. Межагентское общение и арх-решения

- **Вопросы — друг другу, не пользователю.** Нужна ясность → вопрос в блоке «Q&A»
  на доске; партнёр отвечает там же. Пользователя — только если оба в тупике (§6).
- **Ключевые арх-решения — согласовать ДО реализации.** Изменение межмодульного
  контракта / формата persist / публичного API домена / структуры стора / разнесения
  слоёв / split God-модуля — автор пишет в «Арх-решения» на доске, партнёр ставит
  `agreed` или возражает с альтернативой. Реализация — после `agreed`. Для
  рефакторинга это центральный механизм.

## 8. Протокол «стоп / новая задача» + polling без простоя

- **Перед стартом любой задачи:** прочитай этот файл, `COLLAB_BOARD.md` и
  `COLLAB_LESSONS.md`.
- **Polling доски («пила»).** В ожидании монитор `COLLAB_BOARD.md`: старт 30с; пока
  нет задачи для тебя — интервал +5с (30→35→…→60→reset 30). Появилась задача (коммит
  партнёра → нужен review/acceptance, новый item, Q&A-вопрос) — бери и сбрасывай на
  30с. На реальное изменение реагируй мгновенно. У каждого агента СВОЯ независимая пила.
- **«стоп <agent>»** → агент: завершает атомарную правку → пишет snapshot в
  «Состояние» доски (что сделано / что незакоммичено / какие lock держит / следующий
  шаг) → снимает lock'и если встаёт надолго → пауза.
- **«<agent>, задача: …»** → агент: фиксирует задачу в «Активные» на доске (ID,
  статус, lock-файлы) → выполняет end-to-end → по завершении отчитывается метриками
  и ставит `done` (→ ждёт acceptance партнёра, §6).
- Передача управления — только когда дерево зелёное (§2.4) и «Состояние» актуально.

## 9. Отчётность пользователю

- Докладываем, когда ЗАВЕРШЕНА ВСЯ поставленная работа (очередь доски пуста / все
  задачи `accepted`), а не по каждому шагу. Между шагами — координация только через
  `COLLAB*.md` и сообщения коммитов. Работаем в связке и параллельно; пользователь —
  оркестратор (§0).

## 10. Накопленный опыт — отдельный файл

- Грабли и уроки — в **`docs/COLLAB_LESSONS.md`** (пополняют ОБА агента, с `file:line`).
  Читать в начале каждой задачи (§8). При endgame-гонке записи в доску — сериализация
  (один lead ведёт доску, второй пишет отчёт в отдельный файл и встаёт на HOLD).

## 11. Порядок взятия задач — СТРОГО по приоритету

- Задачи берутся НЕ произвольно, а строго по приоритету: сначала ВСЕ `HIGH`, затем
  `med`, затем `low`/feature. Внутри приоритета — user-reported и блокеры релиза вперёд.
- **Запрещено брать low/cosmetic/полиш, пока есть незакрытый `HIGH` в своей зоне.**
- Приоритет проставляет оркестратор (пользователь). Не указан — спроси в Q&A или
  оцени консервативно (user-reported / видимое в проде = high).
