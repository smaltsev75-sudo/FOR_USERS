## Перенесено из sprint-planner-cloud (межстековое — соблюдать с первого дня)

- **Shared-tree verify-contamination (парный флоу на ОДНОМ working tree).** Локальный
  `npm test`/verify видит uncommitted-правки ОБОИХ агентов → может пройти зелёным на
  ещё-не-запушенном коде партнёра; чистый CI краснеет. Рефакторинг = масса
  контракт-изменений (move/rename/export/тип/новый ESM-модуль в `sw.js`-precache) →
  класс особенно опасен. **Правило:** контракт-изменение автор коммитит+пушит ПЕРВЫМ,
  зависимый код — после pull. Авторитетен CI-exit, не локальный verify.

- **Общие файлы (COLLAB_*, package.json, sw.js, index.html и пр.): правь по
  уникальному ТЕКСТ-якорю, не по номерам строк; при коллизии re-read + retry; уважай
  lock.** Параллельная правка одного файла обоими → гонки Edit. Доску намеренно вынесли
  в отдельный `COLLAB_BOARD.md`, чтобы стабильные правила не конфликтовали с волатильным
  планом.

- **Peer-review/субагент-ревью устаревает после любой последующей правки.** Если после
  акцепта партнёра код изменился — нельзя коммитить по старому PASS: обнови доску,
  пометь verdict superseded, запроси повторную независимую проверку.

- **Субагенты систематически фабрикуют (~20% false-positives).** Верифицировать каждый
  пункт adversarial-проверкой, `file:line` обязателен. После использования закрывать
  агента, чтобы не держать idle-процессы. Субагент-review может вернуть FAIL по уже
  добавленному guard'у — сверяй с текущим diff, не спорь с фантомом.

- **Параллельная запись в доску = write-race → при endgame сериализуй.** Один агент
  (lead) ведёт `COLLAB_BOARD.md`, второй пишет свой отчёт/acceptance в ОТДЕЛЬНЫЙ файл
  (напр. `docs/CODEX_SECTION_*.md`) одним коммитом и встаёт на HOLD; lead читает,
  верифицирует лично и пишет final PASS/REWORK на доску сам.

- **Правила-как-текст — тоже test surface.** Если architecture-guard грепает опасный
  паттерн (CSP-директива, XSS-payload, `innerHTML=`, inline-handler), не пиши его
  буквально даже как «плохой пример» в `.md`/комментарии — guard не обязан угадывать
  намерение. Формулируй словами или redacted-плейсхолдером.

- **e2e ≠ domain/service coverage.** Бизнес-логика и нормализаторы требуют unit/
  property-тестов; e2e проверяет UI, не операционную валидность мутаций. Не закрывать
  trust-сценарии (алгоритмы отбора, persistence-roundtrip, migrate corrupt-input)
  только happy-path e2e.

- **Симметричные guard'ы на ВСЕХ мутациях/entry points, не только UI-`disabled`.**
  Каждая мутирующая операция и каждый канал входа данных (startup / import / paste /
  URL / postMessage / SW message) — guard в начале, симметрично. Асимметрия = bypass.
